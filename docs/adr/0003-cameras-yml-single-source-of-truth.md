# ADR-0003: `config/cameras.yml` is the single source of truth, and Frigate's config is generated

- **Status:** Accepted
- **Date:** 2026-09-12
- **Deciders:** project owner
- **Related:** [INV-3](../architecture/invariants.md), [`contracts/cameras-config-schema.md`](../architecture/contracts/cameras-config-schema.md), [`lld/01`](../architecture/lld/01-config-model.md)

---

## Context

PRD §6 requires that cameras be data rather than code: *"This makes adding a camera a
configuration change rather than a programming change."* PRD §2 illustrates the idea
with numbered environment variables:

```env
CAMERA_1_NAME=front-door
CAMERA_1_RTSP=rtsp://...
CAMERA_2_NAME=garage
CAMERA_2_RTSP=rtsp://...
```

That illustration does not survive contact with what a camera definition actually
needs. A real camera has a main and a sub stream, separate credentials, a detection
resolution and framerate, a per-camera object list, per-camera retention, and a
per-camera notification policy. Expressed as numbered environment variables this
becomes `CAMERA_3_DETECT_OBJECTS_2`, which is unparseable, unvalidatable, and
undiffable.

Worse, there are three places camera information is needed:

1. Frigate's own `config.yml`, which requires a specific nested schema
2. Our services, which need camera names, retention, and notification policy
3. The cloud key layout, which embeds the camera name

Hand-maintaining all three guarantees drift. Drift in this system means a camera that
silently is not recorded, or clips written to a path that cleanup does not know about.

Frigate also has its own config file that must exist and be correct, and which
contains substantial non-camera configuration (detectors, ffmpeg arguments, MQTT,
retention, auth) that depends on the host profile.

## Decision

**`config/cameras.yml` is the single, authoritative source of truth for cameras.
`config/frigate/config.yml` is a generated artefact, never hand-edited, marked with a
`GENERATED — DO NOT EDIT` header, and regenerated by `install.sh` and `update.sh`.**

- The schema is YAML with `site`, `defaults`, and `cameras` sections, documented in
  [`contracts/cameras-config-schema.md`](../architecture/contracts/cameras-config-schema.md)
- Generation is deterministic: the same input produces byte-identical output, and
  reordering cameras produces no diff
- Generated files carry a header comment, and the generator records a content hash so
  hand-edits are **detected and refused** rather than silently overwritten
- Validation runs before generation and before any container starts
  ([INV-11](../architecture/invariants.md))
- `.env` retains what `.env` is good at: single-valued, secret, infrastructure-specific
  settings. Camera definitions are not among them
- No camera name or RTSP URL may appear in application source code

## Consequences

### Positive

- **Adding a camera is one edit plus `./update.sh`.** No code change, no Frigate config
  editing, no service reconfiguration
- **Validation becomes possible.** Unknown keys, bad RTSP schemes, `notify.labels` not
  in `detect.objects`, camera name collisions, and undefined `${VAR}` references are all
  caught before anything starts
- **One place to look.** "Where is this camera configured?" has exactly one answer
- **Drift is detectable.** The generated file's hash is compared against the expected
  value, and any discrepancy is reported through health
- **Diffable and reviewable.** Adding a camera produces a readable diff, which matters
  for an open-source project where changes are reviewed
- Comments survive, because the file is the operator's

### Negative / accepted costs

- **A generator to build and maintain.** The mapping from our schema to Frigate's is a
  real component with its own tests, and it must be updated as Frigate's config schema
  evolves
- **An indirection for operators.** Someone who knows Frigate well may be surprised that
  editing `config/frigate/config.yml` does nothing. Mitigated by the header comment, by
  refusal to overwrite hand-edits, and by showing the diff during regeneration
- **Some Frigate options are not expressible** through our schema. A deliberate
  escape hatch is needed for advanced users, and its design is deferred (see
  [`plans/open-questions.md`](../plans/open-questions.md) (moved to `.private/plans/`))
- **Two files to understand**: the source and the generated output. The generated file
  is explicitly labelled as disposable, which helps

### Neutral

- The generated Frigate config is not tracked in git. It is a build artefact
- `config/cameras.example.yml` is tracked and serves as the schema's live documentation

## Alternatives considered

| Alternative | Why not |
|---|---|
| Numbered `.env` variables, as illustrated in PRD §2 | Cannot express nested structure; no validation; ordering changes produce meaningless diffs; a typo is invisible. Workable for two cameras and unworkable for six |
| Hand-edit `config/frigate/config.yml` directly | No camera policy, no retention, no notification config, and no way to keep our services in sync. Guarantees drift across three consumers |
| YAML for cameras, plus manual Frigate config | Half the benefit, all of the drift. The two would diverge on the first camera addition |
| A database as the source of truth, with a UI | Contradicts the packaging premise (PRD §1, §2) and makes configuration invisible to git, diffs, and review |
| JSON Schema or TOML instead of YAML | YAML is what Frigate uses, so operators and contributors already have it; round-trip comment preservation is available via `ruamel.yaml` |

## Revisit if

- The generator's mapping grows complex enough that a simpler direct configuration
  becomes preferable
- Frigate introduces a first-class API for declarative camera configuration, which
  could be a better generation target than a file
- Real usage shows operators consistently needing Frigate options we cannot express,
  in which case the escape-hatch design becomes urgent rather than deferred
